# V3.2 분할 프로토콜

## 1. 왜 V3.1로는 부족한가

V3.1은 held-out goal에서 시험했지만, **실현 예산 정합(`C_rms`)을 그 시험
goal에서 측정**했다. 성능 지표를 최적화한 것은 아니므로 심각한 누출은
아니지만, **공정성 제약이 test에 적응**되었으므로 엄밀한 hold-out이 아니다.

## 2. 5분할 — 블록마다 임무 하나

JBB harmful 100개 goal, `goal_group` 단위로 분할.

| 블록 | 크기 | 유일한 임무 |
|---|---|---|
| `D_direction` | 20 | 거부 방향 `v` 추출, 층 선택 |
| `D_calibration` | 10 | `τ`, `σ`, 자연 margin 이동 `U_Δ` |
| `D_budget` | 10 | 컨트롤러별 이득 `η` 적합 |
| `D_dev` | 10 | 예비 점검, 도달가능성 게이트 |
| **`D_test`** | **50** | **최종 비교 — 동결 이후에만 접근** |

## 3. 분할 방식

* **원문 문자열이 아니라 `goal_group`으로 분할**한다. 같은 목표의 패러프레이즈가
  블록을 가로지를 수 없다.
* 배정은 `SHA-256(salt ‖ goal_group)`의 결정론적 함수다. Python 내장 `hash()`는
  프로세스마다 salt가 달라 재현 불가능하므로 **쓰지 않는다.**
* **범주 층화**: 10개 harm 범주 각각이 모든 블록에 비례 배정된다.

실측 균형 (완전 비례):

| 블록 | 범주당 goal 수 |
|---|---|
| `D_direction` | 모든 범주 2개씩 |
| `D_calibration` / `D_budget` / `D_dev` | 모든 범주 1개씩 |
| `D_test` | **모든 범주 5개씩** |

`split_sha256 = 69e3d8017495efd8f0be97d0fd3c12c8fe61b1b84c5a51524dcc30835b8bd20c`

## 4. 의미 누출 감사

`goal_group`으로 나눴다고 프롬프트가 의미적으로 분리된다는 보장은 없다.
블록을 가로지르는 **모든** 쌍의 토큰 Jaccard 겹침을 계산했다.

| 임계값 | 교차 블록 근접중복 |
|---|---|
| ≥ 0.7 | 0 |
| **≥ 0.6** | **0** |
| ≥ 0.5 | 0 |
| ≥ 0.4 | 3 |

0.4의 3쌍은 템플릿 어구("Write a tutorial on how to…")만 공유하고 목표는
서로 무관하다(폭탄 제조 / 내부자 거래 / 신분 도용). **실질 누출 없음.**

## 5. 동결 이후 규칙

* `η`는 `D_budget`에서만 적합해 `configs/v3_2/frozen_<model>.json`에 SHA와 함께
  기록한다. 최종 시험은 **읽기만** 한다.
* `D_test`에서 측정된 `C_rms`는 **일반화 결과로 보고**한다. 허용 오차를
  벗어나더라도 **재조정하지 않는다** — 그것 자체가 결과다.
* 실행 스크립트는 `PRE_ANALYSIS_FREEZE.json`의 봉인 해시와 대조하며,
  불일치하면 `D_test`를 건드리지 않고 중단한다.
